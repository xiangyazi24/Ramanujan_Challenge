# The central soundness issue: totalized division and `deriv`

Lean's division is totalized. At a zero denominator, `a / 0` is still a term. Consequently the raw expression

```lean
ctRPhi27 n z *
  ((Real.pi : ℂ) / Complex.sin ((Real.pi : ℂ) * z)) ^ 2
```

is **not definitionally the analytic removable extension** at an integer. Mathematical removability does not imply that the raw Lean function is continuous or differentiable there.

Likewise, `deriv f z` is totalized. If differentiability is not proved, Lean assigns a default value. Therefore a calculation involving `deriv` is sound only when it is backed by `HasDerivAt`/`DifferentiableAt` hypotheses or by a theorem whose proof has already supplied them.

There are two separate derivative facts here:

- `ctR27 n` and `ctS27 n` have denominators with poles only at nonpositive integers. On the positive strips crossed in the proof, their denominators are nonzero, so their actual derivatives are legitimate.
- A log-derivative formula containing inverses of numerator factors is **not** legitimate at the numerator's triple zero. The fixed-line log-derivative lemmas from `Problem27Barnes.lean` must not be transplanted to the crossed integer. The factorization must be differentiated directly, using product rules or a proved rational derivative theorem valid at the zero.

For the R term, the local proof must establish the actual factorization

```text
R_n(z) = (z-m)^3 A(z)
```

with `A` holomorphic on the strip. Then, using a genuine derivative computation,

```text
R_n(z) - R_n'(z)/2
  = (z-m)^2 * ((z-m)A(z) - 3A(z)/2 - (z-m)A'(z)/2).
```

The squared sine kernel contributes the inverse square of `z-m`, because

```text
sin(πz) = (z-m) * sineSlope_m(z).
```

Thus the extension is formed only **after algebraic cancellation**:

```text
π² * ((z-m)A(z) - 3A(z)/2 - (z-m)A'(z)/2)
  / sineSlope_m(z)².
```

The S term is analogous. Since `ctS27 n` uses the already-cancelled numerator `ctNumerator27 (n-1)`, it has a triple zero at the crossed integer `m` only under

```text
1 ≤ m < n.
```

This explains why the S one-strip theorem must use `m < n`, not `m ≤ n`.

# Measure-zero singularity audit

A singleton being measure zero solves only an integral-comparison problem. It does **not** solve a Cauchy-theorem problem.

The logically correct division of labor is:

1. Apply Cauchy–Goursat to the holomorphic extension on the entire closed strip, including the integer center.
2. Compare raw and extension on the two vertical boundary lines. Those lines have real parts `m-1/2` and `m+1/2`, so they never contain `m`; pointwise equality is valid for every `y`.
3. For the horizontal limits, compare raw and extension only eventually for `T > 0`. Then the horizontal segment has imaginary part `±T`, so it never contains `m`.

The compile-tested Q6475 transport pattern does exactly this:

```lean
filter_upwards [eventually_ge_atTop (1 : ℝ)] with T hT
exact intervalIntegral.integral_congr fun x hx =>
  heq (top_mem_strip hx) (top_ne_center hT)
```

and similarly for the lower edge. This is sound because `T ≥ 1` proves every horizontal point differs from the center. The corresponding Lean 4.29 audit, run `30703766605`, built successfully and printed only the standard axiom set for:

```lean
horizontal_tendsto_of_eventually_eq
horizontal_bottom_tendsto_of_eventually_eq
top_transport_from_strip_eq
bottom_transport_from_strip_eq
raw_vertical_integral_eq
```

A proof using `intervalIntegral.integral_congr` at `T=0` with an unconditional raw=extension claim would be wrong. A proof using an a.e. equality could ignore the singleton for that one integral, but the holomorphic extension would still be required for the rectangle theorem. The eventual `T ≥ 1` route is cleaner and should be retained.
