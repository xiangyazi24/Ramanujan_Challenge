# Executive verdict

Try the one-shot proof first, but use ring1, not ring_nf:

```javascript
set_option maxRecDepth 100000 in
set_option maxHeartbeats 200000000 in
theorem compact_bracket_factor_49 (b c : ℚ) :
    b * G26 b c * G24 b c ^ 3
      - G23 b c * (F5 b c * F25 b c) ^ 3
      = F7 b c * F49 b c := by
  simp only [
    G23, G24, G26,
    G11, G12, G13, G14,
    F5, F6, F7, F8, F9, F25, F49
    -- add every other project definition occurring transitively
  ]
  ring1
```

A degree-157 polynomial with 3526 monomials in only two variables is large but not automatically beyond ring. Mathlib's tactic normalizes to an internal Horner-style representation; it does not simply emit every distributive rewrite in sum-of-products form. The risky part is the combination of:

- unfolding a 3526-term definition;

- expanding the nested cubes and products on the left;

- large integer coefficients and cancellations;

- constructing and kernel-checking the resulting proof term.

With a 200-million heartbeat ceiling, the one-shot proof is a reasonable experiment. It may succeed. The failure mode may nevertheless be memory exhaustion or excessive elaboration time rather than the heartbeat limit.

My concrete recommendation is:

1. benchmark the one-shot simp only; ring1 in an isolated file;

1. keep it if it uses a tolerable amount of time and memory;

1. if it is fragile, use a closed bivariate-polynomial certificate checked by native_decide, or split the identity into staged ring1 lemmas if avoiding native_decide is important.

Do not start by asking Sage to print a 3500-step Lean proof term.

# 1. Will simp only [all defs]; ring work?

## Why it is plausible

There are only two algebraic atoms, b and c. A polynomial of total degree at most about 160 in two variables has at most

[

binom{162}{2}=13041

]

possible monomials. Thus a final support of 3526 monomials is substantial but not enormous for a sparse bivariate calculation.

Mathlib documents ring as normalizing both sides and comparing the normal forms. Its internal polynomial representation is designed for this purpose, rather than using a naive visible expansion. See:

- Mathlib.Tactic.Ring.Basic

- Mathlib.Tactic.Ring.RingNF

## Why it can still fail

The final monomial count is not the main predictor. The cost also depends on:

- the support sizes of G23, G24, G26, and F25;

- the amount of cancellation between the two large terms;

- the shape of the expression tree generated by the explicit F49 definition;

- coefficient bit sizes;

- whether simp only duplicates large subexpressions;

- recursion depth while traversing a long nested sum;

- proof-term type checking after tactic execution.

In particular, increasing maxHeartbeats does not prevent an out-of-memory failure.

## Use ring1

ring1 is preferable here because the goal is known to be an equality. It runs the core ring procedure and fails directly if the normal forms differ. Ordinary ring has a user-facing fallback that tries to normalize an unsolved goal; on a huge failed identity that fallback can be expensive and can generate an enormous diagnostic state.

Use ring1! only if there is a genuine reducibility/atom-identification problem. Explicitly unfolding the project definitions is more predictable.

## Do not expand powers manually

Keep ^ 3 intact. Do not add pow_succ, mul_add, or distributivity lemmas to the simp set. The ring normalizer handles powers much better than a syntactic simp expansion.

## Practical cost estimate

There is no reliable conversion from “3526 monomials” to heartbeats. For planning purposes, I would expect this shape to cost tens of millions of user-facing heartbeats if the one-shot route is healthy. A rough experimental band of 10^7 to 10^8 is plausible, but it is not a prediction; nested cancellation can move the result by more than an order of magnitude.

A 200-million limit is therefore a sensible test ceiling. I would not commit a monolithic proof merely because it barely succeeds near that ceiling. As an engineering rule:

- below roughly 20–50 million heartbeats with moderate RSS: keeping the one-shot theorem is reasonable;

- around 100 million or more, or peak RSS in the multi-gigabyte range: prefer a certificate or staged proof;

- timeout or OOM: do not keep raising the limit; change the representation.

These thresholds are maintainability guidelines, not mathematical limits.

# 3. ring_nf; rfl is not the faster version

Do not expect

```javascript
ring_nf
rfl
```

to improve performance.

ring_nf uses the same underlying ring normalization machinery, then rewrites the target into a normal form. Its default user-facing form is a sum of products. Materializing and pretty-cleaning a polynomial with thousands of terms is generally additional work. ring1 only needs to normalize the two sides and certify that the normal forms agree.

Even

```javascript
ring_nf (config := { mode := .raw })
```

is primarily useful when the normalized expression itself is needed or for debugging. It still rewrites the goal and constructs the corresponding proof. For a terminal equality, ring1 is the correct first choice.

Likewise:

- norm_num is not a symbolic bivariate polynomial normalizer;

- decide or native_decide cannot directly decide the displayed open equality in variables b,c;

- polyrith and linear_combination do not improve a hypothesis-free polynomial identity and eventually invoke normalization themselves.

# 4. Best pure-Lean fallback: staged normalization

If the one-shot theorem is too expensive, split the normalization at algebraically meaningful boundaries. Do not split it into thousands of distributivity rewrites.

A good staged design is:

```javascript
def G24Sq49 (b c : ℚ) : ℚ := ...       -- CAS-generated expansion
def G24Cube49 (b c : ℚ) : ℚ := ...
def F5F25Sq49 (b c : ℚ) : ℚ := ...
def F5F25Cube49 (b c : ℚ) : ℚ := ...
def LeftA49 (b c : ℚ) : ℚ := ...
def LeftB49 (b c : ℚ) : ℚ := ...
def Bracket49 (b c : ℚ) : ℚ := ...

lemma G24_sq_49 (b c : ℚ) :
    G24 b c ^ 2 = G24Sq49 b c := by
  simp only [G24, G11, G12, G13, G14, F5, F6, F7, F8, F9,
    G24Sq49]
  ring1

lemma G24_cube_49 (b c : ℚ) :
    G24 b c ^ 3 = G24Cube49 b c := by
  rw [show G24 b c ^ 3 = G24 b c ^ 2 * G24 b c by ring]
  rw [G24_sq_49]
  simp only [G24, G11, G12, G13, G14, F5, F6, F7, F8, F9,
    G24Sq49, G24Cube49]
  ring1
```

Continue similarly for the two large summands and the final difference. This lets Lean cache each opaque theorem in the .olean, reduces peak normalization size, and makes a failure local.

A useful alternative is to split by blocks of the outer b-degree. Sage can emit, for example, eight or sixteen Horner blocks rather than 3526 individual monomials. Aim for a few hundred monomials per ring1 lemma.

The staged route is the safest option when the final theorem must remain fully kernel-produced without native_decide.

# 5. Most robust computational fallback: a closed polynomial certificate

The statement with variables cannot be natively decided. A closed equality of polynomial data can be.

Use nested univariate polynomials, which are straightforward executable data:

```javascript
abbrev BiPoly := Polynomial (Polynomial ℤ)

namespace BiPoly

-- Outer variable is b; coefficients are polynomials in c.
def B : BiPoly := Polynomial.X
def C : BiPoly := Polynomial.C Polynomial.X

def pF5  : BiPoly := ...
def pF7  : BiPoly := ...
def pF25 : BiPoly := ...
def pF49 : BiPoly := ...
def pG23 : BiPoly := ...
def pG24 : BiPoly := ...
def pG26 : BiPoly := ...

def lhs49 : BiPoly :=
  B * pG26 * pG24 ^ 3 - pG23 * (pF5 * pF25) ^ 3

def rhs49 : BiPoly := pF7 * pF49

lemma certificate49 : lhs49 = rhs49 := by
  native_decide

end BiPoly
```

Then evaluate the closed identity at arbitrary rational b,c:

```javascript
def evalBC (p : BiPoly) (b c : ℚ) : ℚ :=
  p.eval₂ (Polynomial.eval₂Hom (Int.castRingHom ℚ) c) b
```

Prove once that evalBC respects 0, 1, addition, subtraction, multiplication, and powers, and prove adapter lemmas such as

```javascript
@[simp] lemma eval_pF49 (b c : ℚ) :
    evalBC BiPoly.pF49 b c = F49 b c := ...
```

The final theorem becomes:

```javascript
theorem compact_bracket_factor_49 (b c : ℚ) : ... := by
  have h := congrArg (fun p => evalBC p b c) BiPoly.certificate49
  simpa [BiPoly.lhs49, BiPoly.rhs49] using h
```

This architecture has several advantages:

- the expensive computation is closed;

- the theorem with variables uses only ring-homomorphism laws;

- Sage can generate the coefficient arrays mechanically;

- the result is stable under changes to the pretty-printed scalar expression;

- there is no giant symbolic search in the final theorem.

If your axiom policy distinguishes native_decide, check #print axioms BiPoly.certificate49. The FLT development already uses native_decide for finite certificates in several places, but if this certificate must avoid it, use the staged ring1 route or attempt kernel decide on smaller coefficient blocks.

## Reduce duplication by making polynomial data canonical

The cleanest long-term refactor is to store the 3526 coefficients once, as polynomial data, and define the scalar function by evaluation:

```javascript
def F49 (b c : ℚ) : ℚ := evalBC BiPoly.pF49 b c
```

Then eval_pF49 is definitionally trivial, and there is no second 3526-term expression for Lean to elaborate and maintain.

# 6. What Sage should generate

Sage is excellent for generating a certificate, but not for generating a raw Lean proof term.

Recommended Sage outputs, in descending order of preference:

1. coefficient arrays for Polynomial (Polynomial ℤ) and the closed certificate above;

1. a balanced/Horner-form Lean definition of F49;

1. eight to twenty intermediate expansion definitions for staged ring1 lemmas;

1. coefficient blocks grouped by powers of b, with each block small enough for Lean to verify independently.

Sage should also independently verify:

```javascript
lhs = b*G26*G24^3 - G23*(F5*F25)^3
assert lhs == F7*F49
```

but that assertion is not itself a Lean proof.

## Do not generate a distributivity chain

A Sage script could in principle print thousands of lines such as

```javascript
rw [mul_add]
rw [add_mul]
...
```

or a gigantic calc term. This is usually worse than ring:

- much larger source;

- slow elaboration;

- fragile parenthesization and rewriting;

- enormous .olean files;

- no useful abstraction boundary.

If you want an external generator, have it emit polynomial data plus a small verified evaluator, not individual algebraic rewrites.

# 7. Recommended decision tree

## First attempt

Use:

```javascript
simp only [all custom polynomial definitions]
ring1
```

with local maxRecDepth and an experimental 200-million heartbeat ceiling. Keep powers unexpanded.

## If it succeeds comfortably

Keep the short proof. Record its measured heartbeat count with #count_heartbeats during development, then give it a generous local limit rather than a global module-wide limit.

## If it succeeds only barely

Refactor before committing. A proof that consumes nearly 200 million heartbeats is likely to be fragile under Lean/Mathlib changes and expensive for CI and downstream imports.

## If it times out or exhausts memory

Use the nested-Polynomial closed certificate. This is the most reliable computational solution if native_decide is acceptable.

## If native_decide is not acceptable

Generate staged expansions and prove them with a sequence of medium-sized ring1 lemmas. Split at powers/products or by b-degree blocks; do not split into monomial-level rewrites.

# Final answer to the five questions

1. Will simp only; ring work? It plausibly can, and 200 million heartbeats is a reasonable test ceiling. Use ring1. OOM remains possible, and the monomial count alone cannot decide the outcome.

1. Alternatives? Best robust alternative: closed Polynomial (Polynomial ℤ) equality checked computationally, then evaluate. Best all-kernel-tactic alternative: staged ring1 lemmas with CAS-generated intermediate expansions.

1. Heartbeat cost? Expect a scale of tens of millions if healthy, but measure it. 10^7–10^8 is only a planning band; cancellation and expression shape dominate. Measure RSS as well.

1. Would ring_nf; rfl or decide be faster? No. ring_nf normally does extra rewriting/materialization. Direct decide cannot solve an open equality. native_decide becomes viable only after converting the identity to closed polynomial data.

1. Can Sage generate the proof? Have Sage generate coefficient data, Horner blocks, or staged certificates. Do not have it emit a thousands-line proof chain. Lean should verify the generated certificate through ring1, polynomial evaluation, or native_decide.
